## 1. 목적과 기본 원칙

초기 프롬프트는 단순히 AI에게 작업을 지시하는 문장이 아닙니다.

AI가 프로젝트의 목적과 구조를 이해하고, 앞으로의 작업 방향과 판단 기준을
세울 수 있도록 돕는 **프로젝트 안내서이자 작업 기준**입니다.

초기 프롬프트를 작성할 때 다음 원칙을 따릅니다.

1.  **명확성**: 무엇을 원하는지 구체적으로 전달합니다.
2.  **맥락**: 작업이 필요한 배경과 현재 상황을 설명합니다.
3.  **범위 설정**: 전체 목표와 당장 수행할 작업을 구분합니다.
4.  **작업 분할**: 복잡한 작업은 작고 검증 가능한 단위로 나눕니다.
5.  **검증 가능성**: 결과를 어떻게 확인할지 함께 지정합니다.
6.  **통제 가능성**: AI가 자율적으로 판단해도 되는 범위와 승인이 필요한
    작업을 구분합니다.

## 2. 프로젝트 배경과 목표 설정

AI가 프로젝트를 올바르게 이해할 수 있도록 프로젝트의 전체적인 배경을
설명합니다.

### 2.1 역할 설정

AI가 어떤 관점과 전문성을 바탕으로 작업해야 하는지 지정합니다.

예시:

``` text
너는 시니어 C# 소프트웨어 엔지니어다.
객체지향 설계와 유지보수성을 중요하게 생각하며,
기존 프로젝트의 구조와 코딩 규칙을 존중한다.
```

### 2.2 프로젝트 배경 설명

프로젝트가 무엇이고, 어떤 문제를 해결하기 위한 것인지 설명합니다.

예시:

``` text
현재 프로젝트는 RF 계측기를 제어하고 측정 데이터를
모니터링하는 Windows 데스크톱 프로그램이다.

GUI를 통해 여러 계측기를 제어하고 측정 결과를 표시한다.
```

### 2.3 최종 목표 설정

프로젝트가 최종적으로 달성해야 할 상태를 설명합니다.

예시:

``` text
유지보수성과 확장성을 고려해 계측기 제어 로직과 GUI를 분리한다.
향후 계측기 모델이 변경되더라도 GUI의 수정은 최소화할 수 있도록
계측기별 구현을 독립적으로 관리하는 구조를 목표로 한다.
```

## 3. 작업 정의와 범위 설정

프로젝트 전체 목표와 이번 대화에서 수행할 작업을 구분합니다.

| 구분 | 설명 |
| --- | --- |
| 전체 목표 | 프로젝트가 최종적으로 달성해야 하는 것 |
| 현재 목표 | 이번 작업에서 달성할 구체적인 목표 |
| 작업 범위 | 이번 작업에서 수정하거나 생성할 대상 |
| 제외 범위 | 이번 작업에서 변경하지 않을 대상 |

예시:

``` text
[전체 목표]
계측기 제어 및 모니터링 프로그램 개발

[현재 목표]
계측기 통신 및 명령어 처리 모듈 구현

[작업 범위]
VISA 통신 인터페이스와 기본 명령어 송수신 기능을 구현한다.

[제외 범위]
GUI 화면 및 기존 측정 알고리즘은 이번 작업에서 수정하지 않는다.
```

작업 범위를 명시하면 AI가 요청하지 않은 영역까지 임의로 수정하는 일을
줄일 수 있습니다.

## 4. 명확한 프롬프트 작성

요청 사항은 가능한 한 구체적으로 작성합니다.

다음 네 가지 요소를 기준으로 정리합니다.

  요소        의미        확인할 질문
  ----------- ----------- ------------------------------------------
  **What**    무엇을      무엇을 구현하거나 수정할 것인가?
  **How**     어떻게      어떤 동작과 조건을 만족해야 하는가?
  **Where**   어디에      어느 파일, 클래스, 모듈에 적용할 것인가?
  **Done**    완료 기준   무엇을 만족하면 작업이 완료된 것인가?

예시:

``` text
[What]
todo 삭제 기능을 추가해줘.

[Where]
todo_api.py에 구현해줘.
단, 파일 구조가 적절하지 않다면 먼저 대안을 제안해줘.

[How]
DELETE /todos/{id} 엔드포인트로 구현하고,
존재하지 않는 id를 요청하면 404를 반환해줘.

[Done]
pytest로 삭제 성공 및 실패 케이스를 검증하는 테스트를 작성하고,
테스트 실행 결과를 알려줘.
```

> **참고:** 파일이나 클래스의 위치를 모르는 경우에는 무리하게 지정하지
> 않습니다. AI가 기존 프로젝트를 분석한 뒤 적절한 위치를 제안하도록 할
> 수 있습니다.

## 5. 맥락과 관련 정보 제공

현재 프롬프트를 제안하는 배경과 관련 정보를 제공합니다.

맥락이 구체적일수록 AI가 문제의 원인을 파악하고 적절한 해결 방법을
선택하기 쉽습니다.

### 5.1 제공하면 좋은 정보

-   현재 발생한 문제와 오류 메시지
-   문제가 발생하는 재현 절차
-   개발 환경 및 버전
-   이전에 수행한 작업
-   이미 시도한 해결 방법과 결과
-   기능을 추가하거나 변경하려는 이유
-   관련 코드, 로그 및 설정

### 5.2 예시

**좋지 않은 요청**

``` text
이거 왜 안 돼?
```

**좋은 요청**

``` text
python app.py를 실행하면 다음 오류가 발생해.

ModuleNotFoundError: No module named 'fastapi'

가상환경은 활성화한 상태야.
현재 실행 환경과 패키지 설치 상태를 확인해서
오류 원인을 찾아줘.
```

문제를 설명할 때는 추측한 원인을 정답처럼 제시하기보다, 관찰한 사실과
재현 조건을 정확히 전달합니다.

## 6. 작업 분할

복잡한 작업은 작고 독립적인 단위로 나눕니다.

작업을 작게 나누면 각 단계의 결과를 확인하기 쉽고, 문제가 발생했을 때
원인을 추적하거나 수정하기도 쉽습니다.

### 6.1 한 번에 너무 많은 작업을 요청하지 않기

**좋지 않은 요청**

``` text
회원가입, 로그인, 비밀번호 찾기, 프로필 수정,
이메일 인증까지 전부 만들어줘.
```

**개선된 요청**

``` text
1단계: 회원가입 API를 먼저 구현하자.

- POST /signup
- 이메일과 비밀번호를 입력받는다.
- 중복 이메일은 거부한다.
- 관련 테스트를 작성하고 실행한다.
```

첫 번째 작업이 완료되고 검증된 다음 두 번째 작업으로 진행합니다.

### 6.2 대화 한 번에 하나의 핵심 목표 설정

**좋지 않은 요청**

``` text
로그인을 만들고, 디자인도 바꾸고, 배포도 해줘.
```

**개선된 요청**

``` text
우선 로그인 기능부터 구현하자.
완료 기준을 만족하는지 검증한 뒤 다음 작업을 진행하자.
```

### 6.3 작업 분할을 AI에게 요청하기

작업을 어떻게 나눠야 할지 모르는 경우 AI에게 먼저 계획을 세우도록
요청합니다.

``` text
현재 프로젝트의 전체 목표를 달성하기 위해
필요한 작업을 단계별로 분할해줘.

각 단계마다 다음 내용을 정리해줘.

- 작업 목표
- 주요 작업 내용
- 선행 조건 및 의존 관계
- 예상 결과물
- 검증 방법

전체 계획을 제안한 뒤 우선순위가 가장 높은
첫 번째 작업부터 진행하자.
```

> 복잡한 프로젝트일수록 전체 계획을 먼저 파악하되, 실제 구현은 작은
> 단위로 진행하는 것이 좋습니다.

## 7. 검증 방법과 완료 기준 지정

작업을 요청할 때 결과를 어떻게 확인할지도 함께 지정합니다.

### 7.1 테스트 작성 요청

``` text
todo 추가 기능을 만들고 다음 테스트도 작성해줘.

- 정상적으로 추가되면 HTTP 201을 반환한다.
- 제목이 비어 있으면 HTTP 400을 반환한다.

테스트를 실행하고 각 테스트의 통과 여부를 알려줘.
```

### 7.2 버그 재현 방법 제공

``` text
장바구니 합계가 잘못 계산되고 있어.

[재현 방법]
1000원짜리 상품 2개를 담으면
할인이 없는데도 1800원이 나와.

[요청 사항]
1. 원인을 분석한다.
2. 문제를 수정한다.
3. 해당 재현 사례를 검증하는 테스트를 추가한다.
4. 관련 테스트를 실행한다.
```

### 7.3 실행 확인 요청

``` text
작업 완료 후 서버를 실행해서
/health 엔드포인트가 HTTP 200을 반환하는지 확인해줘.

실행 결과와 확인 방법도 함께 알려줘.
```

### 7.4 검증 결과 보고

테스트나 실행을 수행할 수 없는 환경이라면 성공했다고 가정하지 않도록
합니다.

``` text
실행하지 못한 테스트가 있다면 그 이유를 명확히 알려줘.

다음 항목을 구분해서 보고해줘.

- 실행한 테스트와 결과
- 실행하지 못한 테스트와 이유
- 추가로 확인해야 할 사항
- 남아 있는 위험 요소
```

## 8. 기존 프로젝트 사전 분석

기존 프로젝트를 수정하거나 확장하는 경우에는 구현에 앞서 현재 구조를
파악하도록 합니다.

### 8.1 분석 대상

-   전체 디렉터리 및 파일 구조
-   주요 클래스와 모듈의 역할
-   모듈 간 의존 관계
-   기존 설계 및 아키텍처
-   사용 중인 언어, 프레임워크 및 라이브러리
-   기존 테스트와 빌드 환경
-   프로젝트의 코딩 규칙

### 8.2 사전 분석 요청 예시

``` text
작업을 시작하기 전에 기존 프로젝트를 분석해줘.

다음 내용을 우선 파악해줘.

1. 전체 프로젝트 구조
2. 주요 클래스와 모듈의 역할
3. 모듈 간 의존 관계
4. 기존 아키텍처와 설계 원칙
5. 빌드 및 테스트 환경

분석 결과를 바탕으로 현재 요구사항을 구현하기 위한
적절한 방법을 제안해줘.

기존 설계와 충돌하거나 구조적인 변경이 필요한 경우
구현 전에 변경 이유와 계획을 설명해줘.
```

> 기존 프로젝트에서는 새로운 구조를 무조건 도입하기보다 기존 설계를
> 이해하고 일관성을 유지하는 것이 우선입니다.

## 9. AI 자율성 및 작업 권한 설정

에이전틱 AI는 코드를 제안하는 데 그치지 않고 파일 수정, 명령어 실행,
테스트 수행 등을 직접 할 수 있습니다.

따라서 AI가 독자적으로 판단하고 실행할 수 있는 범위를 지정합니다.

### 9.1 자율적으로 진행할 수 있는 작업

예시:

-   요구사항에 부합하는 일반적인 코드 구현
-   기존 규칙을 따르는 단순한 버그 수정
-   관련 테스트 작성 및 실행
-   작업 결과와 변경 사항 정리

### 9.2 사전 승인이 필요한 작업

예시:

-   전체 아키텍처 변경
-   외부 라이브러리 또는 패키지 추가
-   대규모 파일 및 디렉터리 구조 변경
-   기존 기능에 영향을 줄 수 있는 변경
-   파일 삭제 또는 데이터 초기화
-   외부 서비스에 영향을 주는 배포 및 운영 작업

### 9.3 자율성 설정 예시

``` text
다음 기준에 따라 작업을 진행해줘.

[자율 진행]
- 기존 구조를 유지하는 일반적인 기능 구현
- 단순한 버그 수정
- 테스트 작성 및 실행

[사전 설명 및 승인]
- 아키텍처 변경
- 외부 라이브러리 추가
- 대규모 구조 변경
- 기존 데이터나 파일의 삭제
- 외부 서비스에 영향을 주는 작업

판단이 어려운 경우에는 임의로 진행하지 말고
선택 가능한 방법과 각각의 장단점을 먼저 설명해줘.
```

## 10. 초기 프롬프트 체크리스트

프로젝트를 시작하기 전에 아래 항목을 확인합니다.

-   [ ] 프로젝트의 역할과 배경을 설명했는가?
-   [ ] 프로젝트의 최종 목표를 정의했는가?
-   [ ] 전체 목표와 현재 작업 목표를 구분했는가?
-   [ ] 작업 범위와 제외 범위를 지정했는가?
-   [ ] 기술 환경과 설계 제약사항을 설명했는가?
-   [ ] What / How / Where / Done을 명확하게 작성했는가?
-   [ ] 작업에 필요한 맥락과 관련 정보를 제공했는가?
-   [ ] 복잡한 작업을 적절하게 분할했는가?
-   [ ] 테스트 및 검증 방법을 지정했는가?
-   [ ] 기존 프로젝트를 먼저 분석하도록 했는가?
-   [ ] AI가 자율적으로 진행할 수 있는 범위를 지정했는가?
-   [ ] 사전 승인이 필요한 작업을 구분했는가?

## 핵심 원칙

초기 프롬프트 작성에서 가장 중요한 것은 다음 세 가지를 구분하는
것입니다.

1.  **AI에게 알려줘야 하는 것**: 프로젝트 배경, 목표, 기술 환경,
    제약사항
2.  **AI에게 판단하도록 맡길 것**: 구현 방법, 세부 설계, 작업 순서
3.  **AI에게 확인받을 것**: 아키텍처 변경, 위험한 작업, 테스트 및 완료
    여부

AI에게 모든 것을 지시하려고 하기보다는 **목표와 제약조건을 명확히
전달하고, 세부적인 기술적 판단은 적절한 범위에서 위임하는 것**이
에이전틱 AI를 효과적으로 활용하는 방법입니다.

> 이 문서는 초기 프롬프트 작성 지침입니다. 이후 작업 진행, 코드 리뷰,
> 컨텍스트 관리, 프로젝트 문서화 등의 지침은 별도 항목으로 확장할 수
> 있습니다.
